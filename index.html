What a green backup job won't tell you

“Backup succeeded” means files were copied. It doesn't mean the copy is complete, consistent or usable. These are the failures RestoreProof is built to catch.

How it works

Each test goes through four layers, and each layer gets its own verdict. A check that couldn't run is never counted as a pass.

01 · SNAPSHOT

Pick a real recovery point

Latest, newest-within-24h, pinned, or a random older one, resolved to one immutable snapshot ID.

02 · FILES

Restore into a sandbox

A fresh private directory, verified restore, required files, hashes, and a baseline that catches silent shrinkage.

03 · DATABASE

Prove the data is usable

SQLite opened read-only, or the PostgreSQL dump imported into a throwaway server, then checked with read-only queries.

04 · APP

Boot the real thing

Your app's image on an isolated network with no internet access, health-checked over HTTP. Then everything is removed.

Safe around production, by design

Tests never touch your backups

A recovery test only reads, lists, checks and restores. It can't prune, forget or write snapshots, whether the backups were made by RestoreProof or not.

Polite on a busy host

Restores run at the lowest CPU and disk priority, can be bandwidth-capped, pause while the server is busy, and can be kept to a maintenance window.

Sealed sandbox

Internal network, no published ports, all Linux capabilities dropped, resource limits, and the Docker socket is never mounted into the test.

Careful with secrets

Credentials are encrypted with a key kept outside the database and redacted from every log, report and alert.

Honest results

Signed reports. Crashes and timeouts are never counted as passes. Cleanup is tracked on its own.

Questions

Does a passing test guarantee I can recover?

No, and we won't claim it does. A pass means the stated snapshot restored and passed your checks in an isolated environment. That's strong evidence, not a promise. The report says exactly what was and wasn't verified.

Will it touch my production data or my backups?

No. It only reads from the repository and only restores into its own temporary directories, which it deletes afterwards. It never runs prune or forget.

Which backup tools are supported?

Restic today, on local disks, SFTP, SMB, WebDAV/Nextcloud, FTP, REST server, S3, B2 and Google Drive. Kopia and Borg are next.

When do tests run, and what if one is still running?

RestoreProof has its own scheduler (cron syntax, time zones, optional jitter and maintenance window). One test per app at a time: a slot that comes while the last test is still running is skipped and logged. Missed runs after downtime collapse into one. Only transient problems such as an unreachable repository are retried, a bounded number of times.

Will a big restore slow down my server?

Restores run at the lowest CPU and disk priority by default, can be capped in bandwidth, wait while the host is busy, and can be kept to a maintenance window. For 100 GB+ restores, run the worker on a second machine.

How much disk does it need?

Enough to hold one restored copy of the app you're testing, plus a safety margin. It checks this before starting and stops before crossing your limit.

Is it really free?

Yes. Every feature is free to use, with no limits and no account.

Does anything get sent to you?

No. No account, no telemetry. Alerts go only to the destinations you configure.
